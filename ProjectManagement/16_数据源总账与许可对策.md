# 16 数据源总账与许可对策

> 本文件是 VirtualCity **全工程**(前端控制室 + 后端管线)所有对外数据依赖的唯一总账。
> 每个源记录：谁在用、格式/协议、地址、许可证、能否商用、风险、对策。
> 新增或更换任何数据源时，**必须先在此登记**。

Last updated: 2026-06-27
许可证核实日期：2026-06-27（见文末来源）

---

## 0. 一页结论

- 工程有**两套独立的对外依赖**：前端地图(6 个) + 后端管线(6 类)。
- **商用红线 2 个**（发布游戏前必须换掉）：`FABDEM`(地形) 和 `Esri World Imagery`(卫星)。两者都**禁止商用**或需付费授权。
- **访问风险最高**：`OSM 官方瓦片服务器` 和 `Overpass 公共端点`——社区免费资源，政策禁止重度/商用/离线预取，**可随时撤销**。
- 大多数源换起来很轻：前端是标准 `XYZ 瓦片`，后端可用本地批量包替代实时 API。
- 彻底断奶的两把钥匙：前端用 **PMTiles 自托管底图**，后端把下载数据当**快照资产**沉淀。

## 2. 商用红线（发布前必须处理）

### 🔴 R-1｜FABDEM(#10 地形 DTM)
- 许可 **CC BY-NC-SA 4.0**：**禁止任何商业用途**；商用需邮件联系 `fabdem@fathom.global` 单独授权。
- 影响：你的管线**默认地形源**就是它，意味着当前所有产出都带"不可商用"血统。
- **对策**：发布前把默认 DTM 换成 **Copernicus DEM GLO-30**(可商用·署名) 或 **NASADEM**(公共领域)。
  - FABDEM 本就是"从 Copernicus DEM 去掉森林和建筑"得到的，所以 **Copernicus 是最自然的替换**；代价是森林/建筑密集处地表略不如 FABDEM 干净，但合规彻底。
  - 实操：你 `acquisition/sources.py` 的 dem 兜底链已是 `fabdem → … → nasadem`，把首选改成 copernicus/nasadem 即可，配套加一个"商用导出门禁"(见 §4)。

### 🔴 R-2｜Esri World Imagery(#2 卫星影像)
- Esri 服务条款：**免费仅限"不产生收入"**(无广告、无订阅) + 注册开发者账号 + 署名；**任何商用都需单独付费授权**。
- 影响：只要游戏带任何变现，前端这层卫星底图就违规。
- **对策**：换成可商用的免费卫星源——**EOX Sentinel-2 Cloudless**(CC BY 4.0·署名即可商用) 是最现成的替代；或上 Mapbox/MapTiler 卫星(付费)；或自托管。这一项需要你做个取舍决定。

## 3. 访问风险（不是许可问题，是"随时被掐"）

| 源 | 风险点 | 政策要点 | 对策 |
|---|---|---|---|
| #4 OSM 官方瓦片 | 🔴 政策+可用性 | 禁重度/商用，**禁离线预取/"下载区域"**，无 SLA，可无预警撤销 | 街道底图直接改用 **OpenFreeMap**(你已在用它的 positron) 或自托管 |
| #7 Overpass 公共端点 | 🟡 限流 | 公共实例对自动化大量查询会限流/封 IP | 生产改用 **Geofabrik 泰国抽取包(.pbf) + 本地 osmium/自建 Overpass** |
| #5 Nominatim | 🟡 限流 | 上限 **1 req/s**，仅限终端用户触发的适度使用 | 规模化/商用须**自建 Nominatim** 或用付费地理编码 |
| #3 AWS 地形瓦片 | 🟡 无 SLA | 开放数据集，可商用但无可用性保证 | 关键区域**下载缓存**到本地，不长期依赖在线拉取 |

## 4. 对策框架（落地优先级）

**第一步（低成本、先做）——配置化总账 + 商用门禁**
- 把本表落成一份 `Config/sources.json`：每个源带 `endpoints`(含 fallback 顺序)、`license`、`commercial_ok`、`attribution`。
- 前端与后端**共读同一份**，每条标 `used_by: [frontend|backend]`。
- 加一个 QA/导出检查：**任一层 `commercial_ok=false`(FABDEM/Esri) 即拦住"商业导出"**，把红线从"将来踩雷"变成"管线自动挡住"。

**第二步（彻底断奶的两把钥匙）**
- 前端：用 **PMTiles** 把目标区域底图打包成单文件自托管(你 `web_assets` 已装 pmtiles 库)。
- 后端：把每次下载的原始数据当**带版本的快照资产**归档，而非临时缓存——这也是未来"历史/平行世界时间轴"的物理载体。

**第三步（按需）——适配器**
- 仅当真要换"规格不同"的源时，给该源写一个把它归一化到 `vc_schema` 的适配器。一次只做一个，用真实需求驱动，别提前造万能框架。

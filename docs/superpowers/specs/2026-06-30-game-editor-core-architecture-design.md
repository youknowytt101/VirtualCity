# Game Editor Core Architecture Design

## Goal

Optimize the current game editor from a single large Three.js workbench into a maintainable editor core while preserving the existing WorldBuilder page, workspace switcher, and visual layout.

The target is a medium refactor:

- Keep the current plain browser frontend and static script delivery.
- Use ES modules for editor internals.
- Keep `window.VC_GAME_WORKBENCH` as the public compatibility API used by `workspace.js`.
- Add a clear `SceneDocument`, command system, viewport adapter, runtime layer, and UI adapters.
- Avoid React, Vue, Vite, TypeScript, or a full frontend rebuild in this phase.

## Current Problem

`Scripts/app/area_picker/frontend/game_workbench.js` currently owns too many responsibilities:

- Three.js scene, renderer, camera, lighting, grid, render loop.
- Character creation and stylized material setup.
- Asset drag and drop.
- Whitebox GLB import from Houdini output.
- Scene outline rendering.
- Selection state.
- TransformControls.
- Editor shortcuts.
- Play mode.
- Runtime movement and collision.
- Right panel resizing.

This is workable as a prototype, but it makes the editor hard to extend. A new feature has no obvious home, and scene data is implicitly spread across Three.js objects, arrays, and `userData`.

## Architecture Principle

The authoritative editor state must be a plain data model, not the Three.js object graph.

Three.js objects are a view of the editor state. They may keep `userData.entityId` for lookup, but they must not be the source of truth for object identity, transform, selection, asset references, or editor mode.

All document-changing actions should flow through commands.

```text
DOM or viewport event
  -> Editor command
  -> SceneDocument update
  -> EditorState notification
  -> Three viewport sync
  -> UI panel sync
```

Existing shared scripts stay in place:

- `viewport_grid.js` remains the shared shader grid.
- `asset_dir.js` can stay separate because it is a local asset directory widget.
- `workspace.js` continues to call `window.VC_GAME_WORKBENCH.init()` and `setActive()`.

## Core Model

`SceneDocument` is a plain JSON-compatible object.

```js
{
  version: 1,
  entities: [
    {
      id: "character-01",
      type: "character",
      name: "Player",
      assetRef: "builtin:character",
      transform: {
        position: [0, 0, 0],
        rotation: [0, 0, 0],
        scale: [1, 1, 1]
      },
      collider: {
        type: "capsule",
        radius: 0.36,
        height: 1.76,
        skinWidth: 0.04,
        stepHeight: 0.45,
        walkableSlopeDegrees: 60
      }
    },
    {
      id: "whitebox-terrain",
      type: "whiteboxLayer",
      name: "Terrain",
      assetRef: "houdini:whitebox.glb#terrain",
      collision: {
        enabled: true,
        role: "walkable",
        shape: "triangle-mesh"
      }
    }
  ],
  selection: {
    ids: ["character-01"]
  },
  editor: {
    mode: "edit",
    transformMode: "translate",
    activeTool: "select"
  }
}
```

Rules:

- Entity IDs are stable and generated by `ids.js`.
- Selection stores entity IDs, not object references.
- Transform values live in the document.
- Imported whitebox terrain, buildings, and roads are entities.
- Runtime-only values are not written to `SceneDocument` unless an explicit command applies them.

## Editor State

`EditorState` owns the current document and exposes a small API:

```js
editorState.getDocument();
editorState.dispatch(command);
editorState.subscribe(listener);
editorState.getSelection();
editorState.setEditorMode("edit" | "play");
```

`dispatch(command)` is the only normal path for changing the document.

The state object does not know about DOM nodes or Three.js. It only emits changes.

## Commands

Commands are small objects or functions with explicit execute and undo behavior.

Required first-phase commands:

- `AddEntityCommand`
- `DeleteSelectionCommand`
- `DuplicateSelectionCommand`
- `TransformEntityCommand`
- `SetSelectionCommand`
- `SetTransformModeCommand`
- `ImportWhiteboxCommand`

Command behavior:

- `execute(document)` returns the next document patch or next document.
- `undo(document)` reverses the command.
- Every command that changes the document is added to undo history.
- UI-only changes, such as camera movement, do not enter undo history.

This makes undo/redo a core capability instead of a per-feature patch.

## Viewport Layer

`three_viewport.js` owns Three.js resources:

- `scene`
- `camera`
- `renderer`
- lights
- grid
- render loop
- resize
- entity ID to Three object map

It consumes `SceneDocument` and syncs visible objects:

```text
entity added -> create Three object
entity removed -> remove Three object
entity transform changed -> update object transform
entity selected -> update selection highlight and gizmo attachment
```

The viewport must not directly mutate `SceneDocument`. When a gizmo drag finishes, it dispatches `TransformEntityCommand`.

## Viewport Controls

`viewport_controls.js` owns editor camera behavior:

- right mouse look
- middle mouse track
- Alt orbit
- dolly and zoom
- movement speed

It does not own selection, entity transforms, or play mode.

`transform_gizmo.js` wraps Three `TransformControls`:

- attach by selected entity ID
- set mode from editor state
- emit transform commands after user edits
- block viewport picking while the gizmo is active

## Picking

`picking.js` owns raycast helpers:

- screen to ground
- screen to whitebox surface
- object picking
- walkable hit filtering

The output should be IDs and points, not direct editor mutations.

Example:

```js
const hit = picking.pickEntity(event.clientX, event.clientY);
editorState.dispatch(new SetSelectionCommand(hit ? [hit.entityId] : []));
```

## Asset Import

`asset_registry.js` defines built-in and imported asset references:

- `builtin:character`
- `houdini:whitebox.glb#terrain`
- `houdini:whitebox.glb#buildings`
- `houdini:whitebox.glb#roads`

`glb_importer.js` adapts `window.VC_GLB.load(url)` into editor entities and Three resources.

`houdini_bridge.js` reads the current whitebox contract from `window.VC_HOUDINI_PREVIEW.getWhitebox()` and returns a URL plus identity metadata.

Import flow:

```text
syncFromHoudini()
  -> houdini_bridge.getLatestWhitebox()
  -> glb_importer.loadWhitebox(url)
  -> ImportWhiteboxCommand
  -> SceneDocument contains terrain/buildings/roads entities
  -> three_viewport displays them
```

## Runtime Layer

`play_mode.js` owns entering, updating, and exiting runtime simulation.

Default behavior for this phase:

- Entering play mode snapshots the current document.
- Runtime movement updates runtime objects, not the saved edit document.
- Exiting play mode restores the pre-play document state.
- A future `ApplyPlayResultCommand` can be added if the user wants simulation changes to become edit changes.

This matches common editor behavior and prevents accidental document mutations while testing.

`character_collision.js` owns:

- capsule dimensions
- walkable surface checks
- whitebox floor snapping
- blocking against non-walkable surfaces
- step height handling

Runtime code may read collision entities from the document, but it should not know about UI panels.

## UI Adapters

UI modules subscribe to `EditorState`.

`toolbar.js`:

- drag character asset
- run or stop play mode
- change transform mode
- update pressed states

`scene_outline.js`:

- render scene entities
- show active selection
- dispatch `SetSelectionCommand`

`status_bar.js`:

- show editor status messages
- show load/import/runtime errors

UI modules should not directly manipulate Three.js objects.

## Public Compatibility API

`legacy_bridge.js` exposes the same compatibility surface currently used by the page:

```js
window.VC_GAME_WORKBENCH = {
  init,
  resize,
  setActive,
  loadGLB,
  syncFromHoudini
};
```

Internally this delegates to `editor_app.js`.

This keeps `workspace.js` and `index.html` stable during the refactor.

## Error Handling

- Missing Three.js: fail `init()` with a visible status message.
- Missing `VC_GLB`: fail import with a visible status message.
- Missing whitebox URL: keep the editor active and show an import-specific error.
- GLB load failure: leave the previous scene document unchanged.
- Command failure: do not push to undo history.
- Play mode failure because no playable character exists: keep edit mode and show a status message.

Document-changing commands should be atomic from the user's perspective: either the document changes completely or it remains unchanged.

## Migration Plan

1. Add `editor/` modules and route `window.VC_GAME_WORKBENCH` through `legacy_bridge.js`.
2. Introduce `SceneDocument` and `EditorState` while still rendering with existing Three helpers.
3. Move add, delete, duplicate, selection, and transform mode to commands.
4. Move Three initialization, render loop, lights, grid, and resize into `three_viewport.js`.
5. Move camera controls and TransformControls into viewport modules.
6. Move whitebox import to `assets/`.
7. Move play mode and collision to `runtime/`.
8. Reduce `game_workbench.js` to a temporary shim, then remove it after script references are updated.

Each step should preserve a working editor.

## Testing Strategy

Keep existing Python guard tests during migration, but add behavior-oriented coverage around the new boundaries.

Required checks:

- Workspace still loads the game editor and exposes `window.VC_GAME_WORKBENCH`.
- `SceneDocument` can add, delete, duplicate, select, and transform entities.
- Commands push and undo in the expected order.
- Importing a whitebox creates terrain, buildings, and roads entities.
- Failed GLB import does not mutate the document.
- Viewport creates one Three object per renderable entity.
- Selection updates scene outline and transform gizmo attachment.
- Play mode snapshots and restores the edit document on exit.
- Runtime collision reads whitebox walkable surfaces without mutating editor data.

Browser smoke check:

```text
open editor
  -> add character
  -> select character
  -> change transform mode
  -> duplicate
  -> undo
  -> enter play mode
  -> exit play mode
  -> verify document state restored
```

## Non-Goals

- No full UI rewrite.
- No frontend framework migration.
- No TypeScript conversion in this phase.
- No new build pipeline in this phase.
- No scene saving or publishing implementation in this phase.
- No change to Houdini backend routes.

## Success Criteria

The refactor is successful when:

- `game_workbench.js` no longer owns the whole editor.
- The real scene state is inspectable as a plain `SceneDocument`.
- Three.js objects can be recreated from the document.
- All document edits go through commands.
- Undo/redo has one consistent path.
- Edit mode and play mode have separate state boundaries.
- Houdini whitebox import is an asset/document operation, not an ad hoc scene mutation.
- A developer can add a new editor tool by touching one UI adapter, one command, and optionally one viewport adapter, without reading the entire editor implementation.
